# TrustIQ - Presentation & Demo Prep Guide

## 1. Elevator Pitch
**"TrustIQ is an automated, end-to-end DevSecOps pipeline and Zero-Trust proxy designed to bridge the gap between application development and security. It features two vulnerable target applications (Vanguard and Nova) to demonstrate real-world attacks. TrustIQ then mitigates these through 'Oracle', our custom SAST scanner that catches vulnerabilities before deployment, and 'Veil', a robust Zero-Trust Web Application Firewall (WAF) that actively blocks malicious traffic, enforces authentication, and prevents data leaks in real-time. Everything is monitored and orchestrated through a unified dashboard."**

## 2. Module Breakdown

### A. Vanguard & Nova (The Targets)
*   **What they are**: Two intentionally vulnerable web applications. Vanguard simulates a University portal, while Nova simulates an E-commerce store.
*   **Purpose**: To serve as live targets for demonstrating attacks (like SQL Injection, XSS, Path Traversal, and IDOR) and to prove that our security layers (Oracle and Veil) actually work.
*   **Key Features**: Built with simulated endpoints that fail without security, and succeed when attacked.

### B. Oracle (The SAST Scanner)
*   **What it is**: A Static Application Security Testing (SAST) tool (`scanner.py`).
*   **Purpose**: Analyzes source code *before* it goes live to find security flaws.
*   **How it works**:
    1.  **Regex Matching**: Scans for known patterns of hardcoded AWS keys, database passwords, and API tokens.
    2.  **Shannon Entropy**: A mathematical algorithm that measures the "randomness" of strings in the code. It detects highly random strings (like unknown API keys or encryption keys) that regex might miss.
    3.  **Dependency Checking**: Parses `requirements.txt` against a simulated dictionary of known vulnerabilities (CVEs) to warn about outdated or risky libraries.
    4.  **Dangerous Function Detection**: Flags unsafe Python functions (like `exec()`, `eval()`, or `os.system()`).

### C. Veil (The Zero-Trust Proxy / WAF)
*   **What it is**: A reverse proxy and Web Application Firewall (`proxy.py`).
*   **Purpose**: Sits between the user and the backend to inspect, block, or modify traffic in real-time.
*   **The 6 Core Rules/Protections**:
    1.  **Rate Limiting**: Blocks IPs that make too many requests too quickly (mitigates DDoS and brute force).
    2.  **Payload Injection/XSS**: Scans headers, URLs, and bodies for malicious scripts (`<script>`) or SQL syntax (`' OR 1=1`).
    3.  **Authentication Enforcement**: Rejects requests missing valid authorization headers for protected endpoints.
    4.  **IDOR Protection**: Prevents users from accessing resources that don't belong to them (e.g., stopping User A from viewing User B's profile).
    5.  **Logic/Price Tampering**: Ensures critical data, like the price of an item in a cart, cannot be modified by the client.
    6.  **Egress DLP (Data Loss Prevention)**: Scans *outgoing* responses from the server to ensure sensitive data (like unmasked credit card numbers or raw database errors) doesn't leak to the user.

### D. TrustIQ Dashboard
*   **What it is**: The centralized frontend UI.
*   **Purpose**: Provides a single pane of glass for security engineers. It visualizes the attack logs caught by Veil, displays the code scanning reports generated by Oracle, and allows administrators to toggle security rules on or off.

## 3. Recommended Live Demo Flow

1.  **Introduction**: Deliver the elevator pitch (30 seconds).
2.  **The Code Scan (Oracle)**: 
    *   Show `scanner.py` running or its output on the TrustIQ dashboard.
    *   Point out how it found a hardcoded secret using *Shannon Entropy*.
3.  **The Unprotected Attack**:
    *   Open Vanguard or Nova *directly* (bypassing the proxy, if possible, or just explain what would happen).
    *   Alternatively, turn *off* the Veil proxy rules in the TrustIQ dashboard.
    *   Click an attack button (e.g., SQL Injection). Show how the backend breaks or exposes data.
4.  **The Defense (Veil)**:
    *   Turn the Veil rules *on* in the dashboard.
    *   Click the exact same attack button.
    *   Show the result: The request is blocked (HTTP 403 Forbidden).
5.  **Monitoring (TrustIQ)**:
    *   Navigate back to the TrustIQ Dashboard.
    *   Show the real-time logs updating with the blocked attacks, demonstrating visibility and control.

## 4. Judge Q&A Prep (Anticipated Questions)

**Q1: Why build your own WAF (Veil) instead of using a commercial one like Cloudflare or AWS WAF?**
*   **Answer**: "For a hackathon, building Veil from scratch allowed us to deeply understand the mechanics of request interception and zero-trust principles. While commercial WAFs are standard, our proxy demonstrates our grasp of core vulnerabilities (like IDOR and logic tampering) and how to write custom middleware to stop them at the application layer."

**Q2: How exactly does Oracle detect 'unknown' secrets?**
*   **Answer**: "We implemented Shannon Entropy. It calculates the randomness of a string. Standard text has low entropy, while cryptographic keys or randomly generated API tokens have very high entropy. Even if we don't have a regex pattern for a specific API key, the entropy calculation will flag it as suspicious."

**Q3: What is 'Egress DLP' and why is it important?**
*   **Answer**: "DLP stands for Data Loss Prevention. Most WAFs only look at *incoming* traffic (ingress). Egress DLP inspects the *outgoing* response from our server. If the server crashes and tries to send a raw SQL error back to the user, or accidentally includes a full credit card number, the proxy catches it and masks the data before it leaves the network."

**Q4: What makes this 'Zero-Trust'?**
*   **Answer**: "Zero-Trust means 'never trust, always verify.' Our proxy (Veil) doesn't assume a request is safe just because it comes from a known IP or internal network. Every single request is evaluated for authentication, authorization (IDOR), and payload integrity before it is allowed to reach the backend."

**Q5: How does your IDOR protection actually work?**
*   **Answer**: "When a user requests a resource (like `/api/user/123`), the proxy checks the user's authentication token to see who they actually are. If the token belongs to user `456`, but they are requesting data for user `123`, the proxy blocks it, preventing Insecure Direct Object Reference (IDOR)."

**Q6: What were the biggest technical challenges you faced?**
*   **Answer**: "Integrating the components and handling the networking tunnels (localtunnel) so our local dashboard could communicate reliably with the proxy and backend over the internet. Also, writing accurate regex and entropy algorithms for Oracle to minimize false positives while scanning code."
